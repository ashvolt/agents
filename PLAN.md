# Agents: Level 0 to Pro

A build-and-learn repo. Six taught levels of agent engineering plus three applied ones,
ending in a single production-ready agent that solves a real Sticker Mule operations
problem.

**Owner:** Pragash
**Started:** 2026-09-20
**Stack:** Python 3.13, `anthropic` SDK raw — no agent framework until one earns its place
**Constraint:** job application deadline, so this is a compressed sprint
**Status:** planning. No code written yet.

## 1. The premise

I am not learning agents by reading about agents. I am building several, each adding
exactly one new capability, and then building one more that a company could actually run.

The levels are deliberately small. The capstone is deliberately not.

## 2. Why Sticker Mule

Sticker Mule is a custom print company — stickers, labels, magnets, packaging, apparel.
The business is a pipeline:

```
customer uploads art -> human artist reviews & fixes -> proof sent -> customer approves
   -> printed (next-day) -> shipped
```

The competitive moat is speed plus free human proofing. That moat is also the largest
variable cost: people looking at every single uploaded file.

That is an agent-shaped problem. High volume, a mix of hard rules and real judgment, and
a human escalation path that already exists in the business — which is exactly what a
responsible agent design needs to lean on.

### Candidate capstone problems

| # | Problem | Agent fit | Cost of a wrong answer | Picked? |
|---|---------|-----------|------------------------|---------|
| 1 | Artwork preflight triage — DPI, bleed, cut line, transparency, colour mode, tiny text | Vision plus deterministic checks plus judgment | Bad print, reprint cost | **PICKED** |
| 2 | IP / content policy screening — trademark, copyright, prohibited content | Recall-first classification, tiered escalation | Legal exposure | no |
| 3 | Reprint / refund adjudication — defect photo vs approved proof | Multimodal comparison plus policy plus money | Direct dollar loss | no |
| 4 | Support deflection — order status, address change, cancel window | Straight tool-calling | Low | no |

**Decided 2026-09-20: artwork preflight triage.** The deciding factor was the eval set.
Defects can be injected programmatically, so gold labels are correct by construction — no
hand-labelling and no circular grading. The other three all require labels that would have
to be invented, and an eval set you invented cannot tell you whether the agent is good.

Full brief: [capstone/docs/brief.md](capstone/docs/brief.md).

### Integrity note

This is an unofficial portfolio project. It uses no Sticker Mule data, no Sticker Mule
systems, and no Sticker Mule branding beyond naming the company as the problem domain.
Every dataset is synthetic and generated by me. Every artifact says so on its first page.

## 3. The levels

Each level is one folder with the same four things:

```
levels/L3_single_agent/
  README.md      # the concept, ten minutes of reading, no more
  exercise.py    # stubs plus failing tests. I fill this in.
  solution/      # revealed only after my attempt has been reviewed
  NOTES.md       # what I got wrong, in my own words
```

`NOTES.md` is not optional. The gap between "I read it" and "I can explain it under
pressure" gets written down in that file.

### L0 — Raw API

Messages API, system prompts, temperature, stop reasons, token accounting, streaming.
Cost per call computed by hand.
**Exit test:** I can estimate the cost of a feature before building it.

### L1 — The tool loop, by hand

Tool definitions as JSON schema, `tool_use` and `tool_result` blocks, the loop that drives
them. No framework.
**Exit test:** I can draw the agent loop on a whiteboard, including where it terminates
and where it can hang forever.

### L2 — Structured output and failure

Pydantic schemas, validation, what to do when the model returns garbage, retry with repair
prompts, idempotency.
**Exit test:** my agent survives a deliberately hostile mock that returns malformed JSON
thirty percent of the time.

### L3 — A single real agent

State, conversation memory and its limits, context-window management, real tools (file I/O,
HTTP, a sandboxed shell).
**Exit test:** an agent that completes a multi-step task and recovers from a tool that
errors mid-run.

### L4 — Patterns

Routing, ReAct, reflection and self-critique, planner-executor, parallel fan-out. When each
helps and when it is cargo cult.
**Exit test:** I can name a task where reflection makes results worse, and explain why.

### L5 — Evals (the level that matters)

Building a labelled dataset, exact-match vs rubric vs LLM-as-judge, judge bias and
calibrating a judge against human labels, regression gates in CI, treating cost and latency
as first-class metrics.
**Exit test:** a red CI build caused by an agent quality regression, not a code bug.

> Evals come before the capstone, not after it. Every serious agent role screens for this
> and most portfolios skip it. This is the differentiator.

### L6 — MCP and Skills (folded into the capstone)

Build one MCP server and one client. Write one Agent Skill. Applied to the capstone's real
tools rather than toy ones.

### L7 — Multi-agent (folded into the capstone)

Supervisor and subagents, handoff, parallel workers, shared state. Includes the honest
question: does this capstone actually need more than one agent, or is that
resume-driven architecture?

### L8 — Production (folded into the capstone)

Tracing and observability, token/latency/cost budgets, guardrails and prompt-injection
defence, caching, retries and idempotency, human-in-the-loop queues, graceful degradation,
deployment, runbook, on-call story.

## 4. Schedule

> **Revised 2026-09-20 — the ladder is abandoned.** The original plan taught L0 through L5
> as standalone levels and then started the capstone. That ordering is safer but slower,
> and the deadline does not allow it. L1-L5 are now learned *inside* the capstone, each
> one at the point where the evals show it is needed.
>
> L0 stays in `levels/` as written. It is worth two hours and nothing else works without
> it. Everything above L0 is now capstone work.

The rule that replaces the ladder: **nothing ships unless it beats the previous number.**
The eval harness comes first, a baseline exists before any tuning, and every addition —
tools, a loop, state, a pattern — has to earn its place against that baseline. This is a
harder way to learn, because the first bug is in real code rather than in a toy. It is
also how the job works.

| Day | Work | Level content absorbed | Deliverable |
|-----|------|------------------------|-------------|
| 1 | L0 exercise | L0 | Pricing, stop reasons, token counting. Two hours. |
| 1 | **Capstone gate** | — | Brief, ROI, architecture, data plan. **Done.** |
| 2 | Synthetic dataset generator | L5 (data) | ~200 cases, labels correct by construction, held-out split |
| 2 | Eval harness + metrics | L5 (core) | Runs a callable against the set, reports the metric from section 5 of the brief |
| 3 | v0 agent: full tool loop | L0, L1, L2 | Tool definitions, the loop, structured verdict, validation |
| 3 | **First baseline number** | L5 | Plus the `--no-tools` control arm, to measure what tools actually bought |
| 4-5 | Hill-climb against the eval | L3, L4 | State and patterns added only where a run proves they help; rejected ideas recorded too |
| 6-7 | Production pass | L8 | Tracing, budgets, guardrails, prompt-injection defence, HITL queue |
| 8 | MCP + CI gate | L6 | Tools exposed over MCP; the eval gate runs in CI and can go red |
| 9 | Red team | L5, L8 | Adversarial cases including injection via image content; failure taxonomy |
| 10 | Portfolio | — | README, architecture doc, demo recording, application writeup |

**Slip rule, unchanged:** if a day runs over, cut capstone scope. Never cut the eval
harness or the production pass. A narrow agent with real evals beats a broad agent with
none.

**What the compression costs:** no safe practice reps. The tool loop gets debugged inside
real work with a real eval set watching. Accepted deliberately on 2026-09-20.

## 5. Capstone gate — CLEARED 2026-09-20

All ten items exist on paper in [capstone/docs/brief.md](capstone/docs/brief.md).
Section numbers below point into that document.

- [x] **Problem statement** (brief §1) — one paragraph, in operations language, not AI language
- [x] **User** (brief §2) — art reviewer, support rep, ops manager? Name the seat.
- [x] **Baseline** (brief §3) — what happens today, how long it takes, what it costs
- [x] **ROI model** (brief §4) — cost per decision, volume assumption, expected deflection rate, with
      the arithmetic written out and every assumption labelled as an assumption
- [x] **Success metric** (brief §5) — one number, with a target, that a manager would care about
- [x] **Failure modes** (brief §6) — ranked by what a wrong answer costs. This drives the
      precision/recall choice.
- [x] **HITL design** (brief §7) — what the agent decides alone, what it must escalate, and the
      confidence threshold between them
- [x] **Data plan** (brief §9) — how synthetic cases get generated and labelled, and where they are
      knowingly unrealistic
- [x] **Architecture sketch** (brief §10) — components, tools, data flow, trust boundaries
- [x] **Non-goals** (brief §11) — written down, so scope creep has something to bounce off

Headline from the brief: **auto-approve at least 60% of clean files with a
false-approve rate at or below 1%.** One number, one hard constraint. The eval
gate treats a rise in approval rate bought with false approvals as a regression.

Brief §8 adds an eleventh item the checklist did not ask for: the split between
deterministic checks (code) and judgement checks (the model). That split is the
technical core of the project and the `--no-tools` control arm exists to measure it
rather than assert it.

## 6. What "production-ready" has to mean here

Not "works on my machine with a nice prompt." The capstone ships with:

1. **Evals** — labelled set, judge calibrated against my own labels, CI gate on regression
2. **Observability** — every run traced: inputs, tool calls, tokens, latency, cost, outcome
3. **Budgets** — hard caps on tokens, steps, wall-clock and dollars per task; behaviour at
   the cap is designed, not a crash
4. **Guardrails** — input validation, prompt-injection defence on untrusted content
   (customer-uploaded files are untrusted by definition), output validation before any
   side effect
5. **Human-in-the-loop** — a real escalation queue carrying the agent's reasoning, not a
   `TODO: human review`
6. **Idempotency** — the same order processed twice does not double-charge or double-print
7. **Degradation** — model down, tool down, rate limited: each has a defined behaviour
8. **Runbook** — how to operate it, what the alerts mean, how to roll back
9. **Documented limits** — what it cannot do, and where it is known to fail

Items 4, 5 and 9 are the ones portfolios skip. They are also the ones that tell a hiring
manager whether I have shipped something real.

## 8. Cost and licensing

### Budget

Settled: this is a cheap project. One eval sweep of ~200 cases at roughly 20K input and
2K output tokens per run:

| Model | Plain | Batch API (50% off) | Batch plus caching |
|---|---|---|---|
| Haiku 4.5 ($1/$5 per MTok) | ~$6 | ~$3 | ~$1 |
| Sonnet 5 ($2/$10) | ~$12 | ~$6 | ~$2 |
| Opus 5 ($5/$25) | ~$30 | ~$15 | ~$5 |

Across roughly twenty sweeps plus every level exercise, the ceiling for the whole
fourteen days is **$50-100**. Working rule: iterate on Haiku 4.5, sweep final candidates
on Opus 5, put anything non-interactive through the Batch API, and keep the system prompt
and tool list byte-stable so prompt caching actually hits.

Prompt caching and batching are not cost hacks tacked on at the end. They are L5 and L8
curriculum: cost per completed task is a first-class metric and a standard interview
question. `usage.cache_read_input_tokens` staying at zero across repeated calls means a
silent cache invalidator is at work — that belongs in the eval harness output.

### Open-weight models

Not used for the agent itself. Hosting a local model is a different skill from agent
engineering, it would cost days, and the target role is Claude-API-shaped. The one place
a local model earns a slot is as the **L2 hostile mock** — a cheap generator of malformed
and adversarial output to test the repair path. A plain stub that returns garbage 30% of
the time serves the same purpose for free, so this is optional.

**Re-examined 2026-09-21, specifically for the capstone's vision pass**, and the answer
held — but on arithmetic this time rather than on the scope argument above. At the assumed
4,000 files/day, Haiku 4.5 vision costs ~$2.3K/year against ~$7K/year for a single L4-class
GPU before redundancy or operator time. Self-hosting is *more* expensive here; the
crossover is near 30K files/day. Calibration is the second reason: escalation is
threshold-based, and a confidently-wrong small VLM goes straight through the 1%
false-approve constraint. Full numbers in [capstone/docs/brief.md §8](capstone/docs/brief.md).

One genuine local-model slot did open up, and it is not a language model: a CPU **text
detector** (PaddleOCR / Tesseract / CRAFT) for locating text boxes, which beats any VLM at
that job for free. See the bucket-2 reassignment below.

Everything around the model is open source anyway: pytest, pydantic, ruff,
OpenTelemetry for tracing, MCP as an open protocol.

### Public repo

Yes, public on GitHub — that is the point of the portfolio. Conditions:

**Secrets (do this before the first commit):**
- `.gitignore` covering `.env`, `.venv/`, `__pycache__/`, eval output dirs
- `.env.example` with placeholders only, committed; the real `.env` never committed
- key read via `os.environ` — never a literal in source, never in a notebook output cell
- `gitleaks` or an equivalent pre-commit hook installed

A leaked `sk-ant-...` in public git history is live until revoked and gets scraped fast.
Rewriting history after the fact does not un-leak it — the key must be rotated.

**Everything else:**
- MIT `LICENSE`
- README states plainly: unofficial project, synthetic data, no Sticker Mule data,
  systems or assets
- no scraping their site; synthetic art files are generated locally

**Keep the commit history.** A public repo showing fourteen days of real progression —
early L0 commits, a broken eval, the fix — is stronger evidence than a polished repo with
one squashed commit. Do not tidy the history.

## 11. Skipping the vision model — CV decider now, Jev later

**Decided 2026-09-23.** Founder framing: at 4,000 files/day the vision call cost ~$26/day
while human review of escalations cost ~$950/day. Tokens were never the expensive line;
escalations were. So the question was not "cheaper model" but "can measurement plus a
cheap decider match what the model bought" — which, per results.md §2, was exactly one
thing: escalations from 17.0% down to 13.6%.

**Answer: yes, at $0.** Numbers and method in
[capstone/docs/decider.md](capstone/docs/decider.md).

### Dependencies, and why each earns its place

| Package | Why | Why not the alternative |
|---|---|---|
| `opencv-python-headless` | `connectedComponentsWithStats`: every element's bbox and area in one C pass, which is what the margin-object feature is built on | hand-rolled numpy labelling exists in `text_detect` but returns no per-component stats; headless build avoids GUI/Qt deps |
| `scikit-learn` | fits the decider and runs the out-of-fold model selection | used at training time only — the model ships as JSON coefficients, so inference imports neither sklearn nor pickle |

Rejected: **SimpleCV** (unmaintained, Python 2 only). **scikit-image** not needed yet;
revisit if a skeleton-based stroke measurement replaces run lengths.

### Where Jev fits

Jev (TypeSafe AI, early access 2026-09-15) takes structured state and returns calibrated
probabilities over declared options. It is text-only, so it can never replace the vision
step — it can only replace the decider, which is exactly the slot `Decider` in
`capstone/src/deciders.py` defines. Adding it is one class and one harness arm.

**Decision rule, fixed before any Jev result exists:**

> Jev replaces the logistic decider only if it holds false approves at or below the
> logistic decider's on a fresh sealed holdout **and** either lowers the escalation rate,
> or matches it on a product the logistic model has no training labels for.

Why the second clause: the logistic model already separates train out-of-fold on five
features, so Jev's plausible advantage is not accuracy but day-one coverage of a product
with no labels. Vendor risk (single company, early access, possibly subsidised pricing)
is accepted only because the pipeline runs without it.
