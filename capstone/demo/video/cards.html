Artwork Preflight

Automated print-readiness checking for custom print orders

Every uploaded file is measured against the product it was ordered on, in about a second, for no marginal cost — and cleared, returned to the customer with an explanation, or handed to a person with the findings attached.
Unofficial demonstration project. Not affiliated with, endorsed by, or connected to Sticker Mule. No Sticker Mule data, systems or assets are used. Volume and cost figures are labelled assumptions.

The problem it solves

customer uploads art→human reviews & fixes →proof sent→customer approves→printed next day
  • Free human proofing protects the print, and it is the largest variable cost in the pipeline — it scales one-for-one with orders.
  • Most files are already fine. Reviewer time goes mostly into confirming that nothing is wrong.Assumed: 4,000 files/day · 25% defective · 40 s to clear a clean file · $28/hr loaded
  • 3,000 clean files × 40 s = 33 reviewer-hours a day — about $340,000 a year of expert attention spent on files that needed none.
  • The goal is not to replace the reviewer. It is to stop the clean files reaching them, and to give the broken ones a head start.
Every figure here is a labelled assumption for modelling, not a claim about any real business.

What “good” has to mean here

Auto-approval rate, subject to a false-approve rate at or below 1%

  • A file wrongly cleared becomes a bad print: reprint, reship, a support ticket, and a customer who stops trusting the proof. Call it $18 all-in.
  • At 1% of 2,100 daily auto-approvals that is $378/day — over half the saving. At 5%, the system destroys more value than it creates.
  • So accuracy is the wrong target. The product is tuned to clear as many files as possible under a hard ceiling on wrong clearances, and the release gate fails any build that trades the ceiling for coverage.
Failure ranking behind the design: wrong clearance > wrong fix request > unnecessary fix request > over-escalation > silent crash. Asymmetric costs, so: quick to escalate, slow to approve.

How it decides: three kinds of check

Use code where code is exact. Spend a model only where code cannot go.

1 · file metadata

Exact arithmetic

LOW_RESOLUTION · MISSING_BLEED · WRONG_COLOR_MODE · ASPECT_MISMATCH · UNREADABLE_FILE

Pixel dimensions against ordered size, geometry against the product spec. Same answer every time, microseconds, no cost.

2 · pixel analysis

Measured, not guessed

THIN_LINES · LOW_CONTRAST · UNINTENDED_TRANSPARENCY · TEXT_TOO_SMALL

Morphology, colour distance, alpha analysis and a CPU text detector. Costs compute, not tokens.

3 · judgement

Genuinely ambiguous

Is ink inside the cut margin a logo about to lose its top third, or a background bleeding off the edge on purpose?

The measurement is trivial; the question is not.

Sorting checks into the right bucket is the core design work: an early draft had five checks in bucket 3, and four turned out to be measurement problems in disguise.

Three outcomes. Only one is automatic.

APPROVE
Straight to production, nobody acts. Only when no blocking issue fired and every check that ran is one the system is trusted to make alone.
REQUEST_FIX
Customer acts, from a drafted message. Only off a deterministic check with a concrete, citable measurement. A reviewer approves the message in one click.
ESCALATE
A person acts, with findings attached. Low confidence, conflicting signals, an unsupported file, a detector that returned nothing, or a blown budget.
  • It can never silently clear a file. Every non-approval carries its evidence into the queue, so a reviewer starts from a diagnosis rather than a blank screen.
  • It never edits the artwork and never contacts the customer by itself. Detect, measure, explain — a person keeps the final say on anything that leaves the building.
Uploaded files are treated strictly as data. Text rendered inside an image is described, never followed as an instruction.

How the product was validated

Sealed sets, scored once, reproducible from a manifest and a seed

Question asked of the buildWhat the runs returned
Does it clear enough clean work, safely?78.7% auto-approved · 0 wrong clearances in 500 · exact 95% bound 0.6%
Does it hold up on files customers have mangled?87.0% auto-approved on 480 stress files · 0 wrong clearances in 240
Does a vision model improve the verdict?It changed 1 check of 10, and only reduced hand-offs by 3.4 points
Does letting the model pick its own tools help?No — removing that cut wrong clearances from 33% to 18% at 1.75× less cost
Was the early “perfect” result real?No — it passed at n=88 and breached the ceiling at n=600. Small-sample luck.
The shipped decider is therefore computer vision plus a small logistic model — no model call at inference. Measurement decided that, not preference, and the rounds that went backwards are still published in the product.

How it fits into an operation

service

HTTP API

One call per file: artwork plus order context in, structured verdict out — verdict · issues[] · evidence · customer_message · confidence.

review ui

Queue front end

The page in this walkthrough. Drop a file, see the verdict, the measurements, the marked-up artwork and the draft reply.

agents

MCP server

The same checker exposed as a tool, so an existing support or ops agent can call it directly.

hosting

Runs anywhere

CPU only, no GPU, no key at inference. Also packaged for free hosting, with a runbook and a reproducible report build.

  • Product rules — minimum DPI, bleed, safe zone, minimum text size — live in a spec table per product, so adding a product is configuration, not code.
  • Nothing is stored: an uploaded file lives in a temporary directory for the length of one request.
Logged per check: inputs, measurements, verdict, latency and cost — the inputs to a queue-depth and false-clearance dashboard.

What it does not do yet

Stated here because a tool that hides its blind spots gets trusted in exactly the places it should not be.

  • Not tested on real customer uploads. Real files carry colour profiles, layers, vector-raster mixes and fonts that do not render as expected.
  • Known misses: grey artwork the text detector reads as text, near-white art on white stock, a hairline sitting inside thick ink, and low-resolution art upscaled to look sharp.
  • Cost per file is unproven at production image sizes — demo artwork is roughly a quarter the pixels of a real upload.
  • Zero wrong clearances in 500 is not a zero rate. The exact 95% upper bound is 0.6% — inside the 1% ceiling, but not zero.
  • No adversarial test suite yet, so injection resistance is designed for and unmeasured.
  • Out of scope on purpose: fixing artwork, generating proofs, IP and content screening, pricing, and anything downstream of approval.
All of this is published inside the product, on the results page, beside the numbers it qualifies.

Where it goes next

  • Run it in shadow mode beside the existing queue: same files, no automatic clearance, and compare verdicts against what reviewers decided.
  • Measure the false-clearance rate on real uploads — the one number the ceiling depends on, and the one this dataset cannot settle.
  • Build the adversarial suite, then turn automatic clearance on for the product types where the measured rate supports it.
  • Re-test the optional model on live traffic, and keep it only if the reduction in hand-offs reproduces at scale.
Clean work clears itself. Broken work arrives explained. People spend their judgement on the files that actually need it.
